# Phase 2: 駅東口から始める地理タイル仕様

駅東口200m四方を100m四方の4タイルへ分割した初期試作に続き、1km四方の実データで100/250/500mタイルを生成した。現在の実装・検証結果は [PHASE2_1KM_IMPLEMENTATION.md](PHASE2_1KM_IMPLEMENTATION.md)。以下は当初設計仕様であり、市全域・DEM・基準PCでの実測はなお未完了。

## 現在動く試作

- [タイル表示ページ](../viewer/tiled-preview.html) は `dist/real/fukushima-east/tiles-crisp/tileset.json` と4つのGLBを必要に応じて読み込む。自動移動と矢印キーで地点を移動でき、表示中・読込中・解放回数・FPS・p95・draw callsを表示する。初期は1タイル、境界付近では隣接タイルも表示する。
- `scripts/blender_export_tiles.py` は既存の `city_photo_crisp.blend` の三角形を境界で切り、位置とUVを補間する。`scripts/tile_math.py` はOSM道路線を同じ境界で切り、元道路IDと共有境界ノードIDを保存する。各タイルは元の200m用ローカル座標のままであり、都市全域の投影座標系ではない。
- 出力GLBは順に5,608,052 / 4,715,520 / 13,588,752 / 5,720,300バイト、合計29,632,624バイト。元の単一 `city_photo_crisp.glb` は25,301,644バイト。共有画像が各GLBに重複するため合計は単体より大きい。表示用の壁画像9枚をJPEG品質94・4:4:4へ再符号化して容量を抑え、黒い多角形マスクが必要な3面はPNGを維持した。
- 23件の自動テストが通過。4つの隣接境界で頂点位置・UVが一致し、実道路の14境界ノードは隣接タイル間で座標とIDが一致する。ブラウザーの自動移動でも読み込み・解放が動作し、試した範囲で読み込み失敗0回。低スペック実機での継続動作は未測定。

以下は市全域へ拡張するための**目標仕様**。試作の `tileset.json` は `therabby.geoengine.tileset.prototype.v0.1` で、次の本番用出力契約をまだ満たしていない。

## 空間と座標

- ビルド時に正式な投影座標系、標高基準、変換パラメータをマニフェストで固定する。現行の小区域用 equirectangular 近似を市全域へそのまま延長しない。未知のCRSや鉛直基準は変換を拒否する。
- グリッド原点を投影座標の固定整数メートル値として、`tile_x=floor((east-origin_east)/tile_size)`、`tile_y=floor((north-origin_north)/tile_size)` とする。各タイルの描画頂点はタイル原点からのローカル float32、メタデータの原点は double 精度にする。
- 道路・建物の原本IDはタイルをまたいでも変えない。境界頂点は投影座標の共通値から生成し、隣接タイルで独立に丸めない。境界検査は少なくとも2点の測量済みアンカーで行う。

## 出力契約

本番版の `tileset.json` は `schema`, `projected_crs`, `vertical_datum`, `grid_origin`, `tile_size_m`, `bounds`, `attribution`, `tiles` を持つ。各タイルは `id`, `bbox`, `glb`, `roads`, `terrain`, `level`, `byte_length`, `sha256`, `source_coverage`, `visual_quality` を持つ。URLは相対パス。Cloudflare等の静的ホストで配信できるよう、クライアントはPythonやBlenderを必要としない。

`source_coverage` は面積または件数で `plateau_lod2`, `plateau_lod1`, `osm_only`, `dem`, `missing` を分ける。`visual_quality` は別項目で `photo_reference_repaint`, `official_photo`, `procedural_estimate`, `untextured` を記録する。公式の形状と推定した外観を混同しない。地表高さ、走行可能領域はデータがある場所だけ公開し、不明な地点には `null` と品質フラグを返す。

道路グラフは全域で安定した node/edge ID を持つ別のタイル化JSONにする。道路線を表示タイルで切断しても、元edge IDと境界node IDを双方に保存する。接続検査はグラフの交差点次数・タイル境界の同一座標・経路探索で行う。幅や車線は推定値と公式値を区別する。

## ビルドパイプライン

`取得 → CRS検証/変換 → 空間インデックス → タイルへの面・道路クリップ → LOD生成 → テクスチャ最適化 → GLB/道路/地形出力 → SHA-256付きマニフェスト → 境界/UV/描画テスト`。

1. 同じ入力・設定からタイルID別に再生成できるよう、入力ファイルのSHA-256、取得日、ライセンス、変換器版を記録する。
2. 建物を境界で分断する場合、三角形とUVを共通平面で補間し、原本IDを保持する。初期実装では建物全体を代表タイルへ割り当て、隣接タイルの可視範囲に入る建物を重複ロードしない参照方式を優先する。
3. 道路はタイル境界で線分をクリップするが、トポロジーは全域グラフで保持する。地形DEMは同一格子の共有エッジサンプルを使い、法線の継ぎ目を検査する。
4. 欠損地域はPLATEAU LOD2→LOD1→OSMの順に品質タグ付きで補完する。山間部はDEMを優先する。データがない場所に実在建物のような表現を自動で捏造しない。

## ランタイム読込

- カメラの現在位置と速度から可視タイルを求め、走行方向に1タイル先読みする。読み込み中の重複要求はまとめ、方向変更時には不要な要求を中断する。
- 表示中・先読み中・キャッシュ中を別状態にし、GPU画像メモリの**推定予算**と実測フレーム時間の両方でLRUアンロードを決める。アンロード時にgeometry/material/textureを`dispose()`し、共有テクスチャは参照数を管理する。
- 低LODまたは地表だけを先に表示し、近景LOD2が揃ったら切替える。境界で空白を作らないため、次タイルの表示準備後に旧タイルを外す。
- 運転シミュレータ側へは読込状態、座標変換、道路接続、地表高さ、品質フラグを読み取り専用APIとして渡す。物理・運転評価はGeoEngineに入れない。

## タイルサイズ選定実験

駅東口200mだけでは500mタイルの妥当性を判定できない。Phase 2では少なくとも連続1kmの実データが取得できる区域で同一素材を100m、250m、500mの3設定で出力し、以下を測る。

| 候補 | 200m試験での傾向 | 測るべき点 |
|---|---|---|
| 100m | 4タイル、細かいアンロードが可能 | 要求数、境界の接続、draw call |
| 250m | 現行区域をほぼ1タイルに収める | 先読み距離、ピーク画像メモリ |
| 500m | 現行区域より大きく、比較不能 | 走行時のロード停止とメモリピーク |

共通の自動移動経路・1280×720・同じ画質で、初期表示時間、タイル交換時p95/p99、100ms超フレーム数、通信量、ピークメモリ推定、draw callsを比較する。100/250/500mの採用値はこの実験後に決める。

## Phase 2 完了条件

駅東口を複数タイルで動的表示し、境界通過で道路接続と建物位置が保たれる。ロード/アンロード/先読みが動作し、元の単一GLBと同じ出典・品質表示を保持する。基準PCの30FPS/10分安定性と市全域の収録率は、Phase 2だけでは完了扱いにしない。
