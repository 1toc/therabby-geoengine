# 福島駅東口 v0.3 第2段階：写真10枚の遅延取得

`start_station_lod2.cmd` で配布版を起動後、`viewer/citywide-v1.html?station_lod2=1&photo_stream=1` を開く。通常の300m表示と前段の `photo_pilot=1` は維持する。

## 対象と生成

100m境界はEPSG:6677の中心 (55386.87527250558, 194867.2860515836) から各50m。`scripts/build_station_photo_stream.py` は既存の2025 PLATEAU LOD2 High/Low GLBと公式JPEGのSHAを照合し、100mに交差する10棟の10写真を `data/derived/station-photo-pilot/` へ複製する。元GML・JPEG・GLBは変更しない。`stream.json` は建物ID、写真ID、材質名、元画像URI、Low GLB、画像解像度、JPEGサイズ、投影座標の外接矩形、出典を記録する。10枚合計1,003,844バイト、RGBA8とミップマップの概算68.0MiB。写真は256×512から2048×1024などを含む。Low GLBだけを初期ロードし、元JPEGは距離35m以内で個別に要求する。55m超でHighテクスチャを破棄する。

表示材質を写真IDごとに束ね、同じ材質を使う複数メッシュに同一Highテクスチャを設定する。元Lowテクスチャは変更しない。Highには独立した `THREE.Source` を使い、離脱時に材質をLowへ戻してからGPUテクスチャを `dispose()`、ImageBitmapを `close()` する。GLBの形状・UV・indexは両解像度で一致することを自動試験で確認した。写真の向きはGLTFLoaderと同じ `flipY=false` にしている。

同時処理上限は初期3件、High展開画像の推定上限は128MiB、再訪用の圧縮JPEGキャッシュは4MiB。設定は画面で変更できる。近い写真から優先し、容量が足りなければLowを表示してLRU順にHighを解放する。JPEGキャッシュも上限超過時は古い写真から削除する。取得ごとにSHA-256を確認する。404等はLowを維持し10秒待って再試行する。タイル変更・離脱時に要求を中止し、古い結果は世代番号と距離で拒否する。ブラウザのHTTPキャッシュとアプリ内JPEGキャッシュ、GPUテクスチャは別の資源である。

画質比較は[同一視点のA: Low / B: 全117枚元JPEG](evidence/station_photo_stream_ab.png)、[C: 動的10枚](evidence/station_photo_stream_c.png)、[A/B計測JSON](evidence/station_photo_stream_ab.json) を保存した。A/Bは開発RTX 3060、950×720描画バッファで各3秒、双方約60FPSの垂直同期上限。撮影した視点ではCとAの画素差が0で、CのHigh化した材質が画面で見えていない可能性がある。**CがBと同等の見え方になったとは判定しない。** 材質を確実に画面へ向けた専用比較視点の整備が次の課題。これらは基準PCの30FPS判定ではなく、WebGLテクスチャ数はGPUメモリの実割当容量ではない。

自動試験60件、JS構文検査、配布版のハッシュ検証を実施する。テスト未実施は実機Intel内蔵GPU/8GB、ネットワーク応答途中の中断、長時間走行と他の100m区域。全117枚へ拡張する際は、材質・写真の共有関係、タイル解放の寿命、異なる位置の混雑時の優先順位、圧縮JPEGキャッシュ容量、画面に見える壁での画質差、実機の長時間メモリ増加を確認する。

## 117枚の鮮明表示モード（追加検証）

`viewer/citywide-v1.html?station_lod2=1&photo_stream=all` では、300m区域の全117枚を外部JPEGの候補にする。`scripts/build_station_photo_stream.py` が元GLB中の写真と出典SHAを照合し、`stream-full.json` と117個のJPEG派生ファイルを生成する。元GLBと元JPEGは変更しない。写真JPEG合計17,691,580バイト。全枚数をRGBA8とミップマップで同時展開した理論容量は889.83MiBなので、起動時に一括ロードしない。初期表示はLow GLBだけで、カメラから90m以内かつ視錐台に入る写真を距離順で取得し、130mを超えると元JPEG用のGPUテクスチャを解放する。高画質写真の推定展開容量は初期128MiBを上限とし、画面で調整できる。予算不足では近い写真を優先する。描画倍率は初期Mediumで、画質選択からHighへ変更できる。写真の元画像に含まれない細部は補完しない。

117枚中66枚はLowへの変換で縮小されており、51枚は元画像から画素数が増えない。鮮明表示モードでは後者51枚の元JPEG取得を省き、容量を画質差のある66枚に回す。元画像自体が低解像度の場合は画像処理で実在しない細部を作らない。

開発ブラウザの地上視点では、容量上限を1MiBにしたLow比較から128MiBへ戻すと、表示Highが1枚から10枚になり、近景の壁面と窓の境界が目視で明瞭になった。観測時はHTTP同時最大3、High推定127.7MiB、取得16件、失敗0件だった。同一視点で1MiBへ戻した際、Highは1枚、推定0.7MiBに戻り、壁面が再びぼやけた。これは短時間の開発ブラウザ観測で、画質の数値評価や基準PC性能の保証ではない。元JPEGが小さい写真や元写真自体がぼけている壁面、写真のない面、LOD1遠景は鮮明化できない。Intel内蔵GPU/8GBでの実測と長時間移動時のメモリ安定性は未実施。

視錐台優先の調整後、配布版をローカルHTTPで再起動して確認した。初期高解像度JPEG取得0件、地上視点でHigh適用5件、HTTP同時最大3、推定High保持80.0MiB、コンソール警告・エラー0。自動試験61件、JS構文検査、配布版2,345ファイルのSHA-256検証が通過。`start_station_lod2.cmd` はこのモードを既定で開く。v1.0受入と基準PCの性能測定は引き続き未完了。

## 駅前の歩行モード

「駅前を歩く」で道路近くの地上視点へ移り、WASDで移動、画面ドラッグで視点変更、Shiftで少し速く移動する。「歩行を終了」または「俯瞰」「地上」で従来操作へ戻る。歩行は駅前300m四方に限定し、DEM5A地形の高さに目線を1.6m合わせる。地形・駅前建物が未読込、地形欠損、急な段差では移動を止める。駅前の表示中の建物メッシュに対し、進行方向に3つの高さと左右3点の短いレイで壁を検出する簡易判定を使用する。体積を持つ完全な衝突判定ではなく、建物内部からの脱出、窓や入口、薄い壁、段差、橋・トンネル、歩道の正確な通行可否は未保証で、運転評価・安全判断には使えない。

開発ブラウザで歩行開始、WASD前進、右方向への連続移動と壁接近時の停止を確認した。内蔵GPU・8GBでの速度、区域全体の通行検証と複雑な地形・建物との衝突検証は未実施。

歩行中も俯瞰用OrbitControlsの更新がカメラ位置を動かし、上下の視点変更で浮遊する不具合を修正した。歩行中はOrbitControlsの更新を止め、独立した視点操作を使う。開発ブラウザで上方向へのドラッグ前後の目線標高が71.07951mで一致し、上を見ながら1.5秒歩いた後は地形追従により71.08239mになったこと、歩行終了への切替とコンソール警告・エラーなしを確認した。これは一地点の確認であり、全区域や実機性能の検証ではない。

壁面確認や写真詳細の視点移動を選ぶと歩行を終了し、歩行状態のまま別視点へ飛んで移動できなくなる不具合を修正。地形の高さ変化制限を移動距離に応じて調整した。写真の試験設定は初期状態で折りたたみ、必要に応じて開く。Low画質では追加の鮮明化を停止し、非表示中は描画を休止する。開発ブラウザで歩行から各視点への切替、前進、建物への接近停止を確認。歩道と車道の境界・路面高さの現地照合、写真の高解像度化、基準PCでの性能は未完了。

駅前LOD2の形状を保持し、描画時に壁面へ規則的な仮の窓と壁色を生成する。窓は写真や実測を解析したものではなく、窓の有無・大きさ・配置・階数・建物の用途や色を正確に表すものではない。屋根なども簡略化され、煙突や斜めの壁面に不適切な模様が出ることがある。AIの比較画像のような建物ごとの外装デザイン、地上階の店舗、凹凸は未実装。駅前300mのLOD2のみに適用し、市街地全体のLOD1やOSM補完建物は対象外。元の写真やGLBは変更しない。

駅前117写真の対応材質ごとに、元JPEGの黒い空白を除く画素の中央値から概略色を算出し、建物IDに基づく固定ルールで窓の幅・間隔・配置を変える。色の算出には屋根や窓も混じるため実際の外壁色の測定ではない。`scripts/build_station_style_profiles.py` はPillowを必要とする開発時の再生成処理で、画像のSHA-256を照合して `viewer/station-style-profiles.js` を生成する。写真のない材質は共通の推定値を使う。規則に基づく色・窓配置であり、個別の建物を目視で採寸したものではない。

### 駅前全写真への共通鮮明化

`公式写真を鮮明化（駅前全体）` はLOD2の写真マテリアルに共通の描画時アンシャープ処理を適用する。テクスチャの実際の幅・高さに応じた近傍4点を参照し、弱い差分を抑制し、補正幅を制限する。117写真の対応マテリアルがLow GLBに存在することを自動試験する。全画像を一括取得するものではなく、既存の90m以内・視錐台・128MiB予算の元JPEG遅延取得を維持する。画像ファイル・UV・実際の建物形状は変更せず、画像にない看板や窓は生成しない。画像が低解像度または元々不鮮明な場合は限界があり、鮮明さを上げるとノイズや輪郭の強調が生じる。鮮明さは画面で調整でき、「公式写真」で補正なしに戻せる。写真のない面、駅前以外のLOD1・OSM建物には効果がない。

開発ブラウザで117棟の写真表示、同じ壁面の補正あり・なし、元JPEGの遅延取得およびコンソールを確認した。4回の追加テクスチャ参照が必要なため、基準のIntel内蔵GPU・8GBでは性能未測定。開発環境の短時間表示を基準PCでの30fps達成として扱わない。
