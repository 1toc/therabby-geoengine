# 駅東口 v0.2：写真画質と道路面（開発プレビュー）

対象は福島駅東口の中心 `37.75445, 140.46190` から東西・南北各150m。既存の全市タイルビューア `viewer/citywide-v1.html?station_lod2=1` に追加した。旧v0.1 HTMLと車両制御は変更していない。

## 写真ぼけの原因と前後比較

`scripts/audit_station_texture_v02.py` が公式2025 CityGML付属のJPEG 117枚、Low / Medium / Highの埋込GLB画像、glTFサンプラを実際に読んだ結果は [監査JSON](evidence/station_texture_v02_audit.json) にある。

![同じ公式写真の中心部分を元画素の縮尺で比較。左から原本、Low、Medium、High](evidence/station_texture_v02_source_variants.png)

- Highの117枚は元の公式JPEGとSHA-256がすべて一致。Highへの変換時の画像再圧縮やアトラス縮小はない。UVの保存は既存の `tests/test_station_lod2_overlay.py` と `tests/test_phase1.py` でも検査する。
- Lowでは66/117枚、Mediumでは33/117枚を縮小している。原画像は128px級から4096px級まで混在し、元画像そのもののピント・解像度も建物ごとに異なる。比較画像のHighにも元からのぼけが残る。
- glTFサンプラは `magFilter=9729`（線形）、`minFilter=9987`（線形ミップマップ）。KTX2は使っていない。異方性はLow 2、Medium 4、High 8（端末上限で制限）。画面描画倍率はLow 1、Medium最大1.5、High最大2で、実バッファ画素数を画面で確認できる。
- 画面の「写真の斜め方向フィルタ」で4倍と8倍を、「写真の縮小フィルタ」でミップマップありと線形補間のみを、その場で切り替えられる。通常は画質モード連動とミップマップありを使う。これらの単独切替によるFPS・画質の定量差は未測定。
- 駅前写真はGLBで配信しており、3D Tilesの `errorTarget` とタイルキャッシュ容量はこの表示経路に適用されない。大きいGLB2枚を元画像品質で近景だけに細分して読み込む仕組みは未実装。
- 「駅前写真の解像度」を全市画質モードから独立して切り替えられる。元JPEGを選ぶと、同じLow描画倍率で写真縮小だけの影響を比較できる。GPU画像のRGBA8+ミップマップ理論値は全117枚表示時、Low約95 MiB、Medium約272 MiB、High約890 MiB。これは**実GPU割当量ではなく**画像画素数からの上限見積もりで、幾何形状などを含まない。

同一の地上視点でLowと元JPEGを切り替え、ビル外壁の窓線・目地が元JPEGでやや見えること、同時に原写真由来のぼけが残ることを確認した。上の比較図は公式元JPEGと実際のGLB埋込画像を同じ領域で表示したもので、Three.js画面のスクリーンショットではない。シャープ化や生成AI補間はしていない。

![同じカメラ・描画バッファでのブラウザ画面比較。左Low、右公式元JPEG](evidence/station_photo_v02_browser_low_vs_source.png)

[ブラウザ比較計測JSON](evidence/station_photo_v02_browser_low_vs_source.json) は開発PCのRTX 3060、1280×720ブラウザ表示（3D描画バッファ950×720）、Low画質の地上視点で撮影した。各モード3秒・180フレームの観測ではLow 59.98 FPS、元JPEG 59.98 FPS、p95とも16.8ms。Lowは再読み込みなし、元JPEGへの切替は約1.0秒。写真のRGBA8+mipmap理論値は約95→890MiB。WebGL登録テクスチャ数は表示範囲とアップロード状態で変動するため、GPU実メモリ容量の測定ではない。この短時間・開発環境・垂直同期上限60FPSの観測から、基準PCの性能や長時間安定性を推論しない。

## 道路面の変更

### 2026-11-07 地形との表示段差の調整

駅前の元5m標高格子と表示中の市全域地形メッシュには差があり、61×61地点で後者が最大約40.6cm高かった。道路が埋もれる問題を軽減するため、`scripts/build_station_visual_terrain.py` で表示地形と同じ三角形を抽出し、その面を補間する。公式道路区域は表示地形上8cm、OSM由来の推定路面は12cmに配置する。駅前300m内では道路帯の両端と交差点パッチの周縁も地形に合わせる。範囲外は従来どおり端点の地表高を補間する。オフセットは表示上の重なり対策であり、実路面高ではない。道路区域と推定路面の精度、Z-fighting、現地との照合、対象PC性能は別途実機確認が必要。

再生成は `python scripts/build_station_visual_terrain.py`。入力タイルのSHA-256と座標系を検証し、地形が読み込めない場合は旧格子へフォールバックする。2026-11-07は合成三角形の補間と駅前61×61地点の地形カバーを確認した。ブラウザ画面・基準PCは未検証。全テストはPython 3.15環境のPillow不足で5モジュールが読み込めず未完了。

従来はOSM中心線の各線分へ推定幅を付けた黄土色の平面帯のみだった。v0.2では次を表示する。

1. 公式PLATEAU / 福島市2025 `tran` LOD1道路外形を300m範囲へ切り出した43面。`scripts/build_station_roads_v02.py` が既存のソース検証済み1kmデータとDEM5A 5mグリッドから [配布用JSON](../data/derived/fukushima-station-roads-v02/road_extent.json) を生成する。EPSG:6697の元高さ0は実路面高に使わず、投影EPSG:6677とT.P.地表高を明記する。
2. 公式外形をDEM5Aへ沿わせるため、約8mより長い三角形辺を分割し、頂点をDEM地表 +0.13mへ配置する。外形には車道と歩道の境界がないため、灰色の「道路区域」として描く。
3. OSM中心線は道路分類と既存の概略幅を保持し、最大8mごとの帯、接続ノードの円形パッチでアスファルト面を連続表示する。駅前はDEM5Aの中間点地表高も使う。表面の微細な粒は手続き生成の軽量128pxテクスチャで、現地路面の写真ではない。PBR材質、ミップマップ、異方性を使う。歩道系タグは明るい舗装色で視覚区別する。
4. 橋・トンネルは高さが不明のため地表道路面を生成しない。公式外形とOSM帯は異なる小さな高さオフセットを付け、Z-fightingを避ける。道路中心線、公式外形、路面質感、高さ説明を個別切替できる。

OSMの幅が分類から推定された箇所は引き続き推定である。`tran` は車道の実測幅・歩道の位置・車線区画線・横断歩道・橋面高を提供しない。道路面の継ぎ目を埋めても、車両衝突用の連続路面、合法走行、標示位置が検証済みという意味ではない。区画線・停止線を正確な実データとして追加していない。

駅前300mに中点がある現行OSMタイルの253線分を点検すると、幅員は全253線分が道路分類による推定、車線数タグあり7線分、橋タグあり0線分、トンネルタグあり19線分。`steps` 13線分は平坦な舗装面に変えず表示を省く。現行の派生道路タイルは `layer` タグを保持していないため、重層交差の正確な判定は未実装。元のOSMタグを用いた再生成と立体交差の個別検証が必要。

## 再生成と検証

開発PCのみPythonとPillowが必要。ブラウザにはインストール不要。既存のPythonパスを `$python` に設定後：

```powershell
& $python scripts/build_station_roads_v02.py
& $python scripts/audit_station_texture_v02.py
& $python -m unittest discover -s tests -v
& $python scripts/package_citywide_preview.py
& .\verify_citywide_preview.ps1
```

確認済み：公式写真117枚のSHA一致、43道路外形と61×61 DEM格子の整合、未知の鉛直基準を拒否するテスト、ユニットテスト、JavaScript構文、開発PCブラウザで駅前地上視点・道路面・写真解像度とデバッグ表示切替・コンソールエラーなし。`dist/citywide-v1-preview` はコピー後にSHA-256検証し、同パッケージ内のビューアでも写真117棟・道路面を表示した。比較画像・JSONを配布版にも含める。

未検証：基準PC（Intel内蔵GPU / RAM 8GB）の30fpsと10分安定性、GPUの実メモリ割当、元JPEG品質の大量タイル読み込み時の負荷、建物・道路の測量点照合、橋・トンネル、車道/歩道分離、路面材の現地一致、走行・衝突判定。次段階では写真GLBを小さな近景単位へ分割し、近傍のみ元解像度を読み込む。`tran` の詳細LODまたは別の正確な道路面データが得られたら車道と歩道を分離する。
